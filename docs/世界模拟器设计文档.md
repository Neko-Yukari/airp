## 〇、项目初衷

当前 AIRP（AI 角色扮演）工具普遍停留在纯粹的提示词工程与上下文狂塞阶段，并以高缓存率为卖点。这一路线存在根本性问题：

1. **对运行无用的上下文注入没有意义**——大量与当前视角无关的信息稀释了有效上下文；
2. **transformer 架构的固有缺陷**——"不要做 X"式的负向约束会导致模型刻意地"做 Y（不做 X 版）"；持有不该知道的信息的模型，会以各种方式泄漏它（"A 不知道 B 的秘密，但 A 的生成故意提到了 B 的秘密"）。

因此本项目的核心主张是：

> **只注入对玩家有意义、对当前视角有意义的内容。信息隔离由世界模型的结构保证，而不是靠提示词约束 LLM 的自觉。**

项目本质上是一个**带叙事界面的世界模拟器**，而非"对话前端 + 提示词工程"。与酒馆类工具不是一个物种。

## 一、总体架构

**一句话定位**：一个以信息流为核心动力学、以组件化实体数据为状态骨架、以成熟桌游规则为判定基础、由管理者调度场景内实体 agent 的独立世界模拟器；LLM 负责实体扮演、叙事与语义裁定，引擎负责提交和保存世界状态。WebUI 或未来的游戏引擎只是可替换的交互适配层。

**硬性原则**：

> 世界状态、信息权限、控制关系和事件提交由引擎维护；成熟规则包处理稳定判定；管理者在场景内组织实体 agent 行动，LLM 处理扮演、叙事和语义判断。LLM 产生的行动与裁定进入事件流程，由引擎记录其依据并提交最终状态。

### 分层结构

```
┌─────────────────────────────────────────┐
│  交互层：管理员 agent = 玩家对世界的交互页面  │
├─────────────────────────────────────────┤
│  场景协调层：管理者调度实体 agent             │
├─────────────────────────────────────────┤
│  LLM 接入层：扮演、叙事与语义裁定接口          │
├─────────────────────────────────────────┤
│  规则层：成熟桌游规则包与混合判定              │
├─────────────────────────────────────────┤
│  模拟调度层：LOD + 热度系统                 │
├─────────────────────────────────────────┤
│  信息流动层：信息的产生、传播、畸变、遗忘      │
├─────────────────────────────────────────┤
│  世界模型层：ECS，事实/认知双层，事件日志     │
└─────────────────────────────────────────┘
```

## 二、已确定的设计决策

### 2.1 世界模型层

- **空间包含结构（已确定）**：世界 → 大陆 → 国家 → 聚落 → 建筑等空间与行政包含关系可采用树形或有向无环结构。
- **多图关系结构（已确定）**：人物还会同时处于社交关系、信息通道和控制权关系中，这些关系以带类型的图表达。关系类型来自可扩展注册表，而不是写死在字段枚举中；运行期间可以增加新的关系类型，无需迁移人物主结构。
- **关系允许并存和变化（已确定）**：同一方向上的两个人物可以同时具有多种关系，例如“朋友 + 雇佣关系 + 债权关系 + 暂时敌对”。关系通过新增、结束或更新关系实例发生变化，不以单个标签互相覆盖。
- **关系分层（已确定）**：初始关系目录至少区分“当前态度”（友善、警惕、敌对等）、“情感纽带”（朋友、亲人、爱人、宿敌等）和“社会角色”（父母/子女、师傅/学生、雇主/雇员等）。关系默认按有向记录处理，A 将 B 视为朋友不自动推出 B 也将 A 视为朋友。
- **独立 agent 粒度（已确定）**：人是最小的、拥有独立 agent 空间的单位。人物、组织、地点、物品、信息等仍可作为不同类型的 ECS 实体存在；军队、国家等实体可由人物 agent 操控，但自身不必拥有与人物相同的独立 agent 空间。
- **事实/认知双层（已确定）**：
  - 引擎保留可查证的**权威事实层**：事实 = 已提交事件日志 + 实体状态（如“领主状态：死亡”）。
  - 权威事实只通过视图查询和信息流动进入 agent 上下文；每个人物持有自己的**认知副本**。
  - 认知可以与事实偏离（如传闻"领主被复活成僵尸"），系统任其自然，不予纠正。
- **UUID 一致性方案（已确定）**：实体、物品、信息均拥有 UUID。信息有 UUID 后可建立**溯源链**：信息 #4471 在传播中畸变为 #4523，两者指向同一原始事件但内容不同。实体引用信息即引用 UUID，"谁说的、从哪听来的、传了几手"全部可查证。Agent 通过查 UUID 获得一致性。
- **ECS 组件化（已确定）**：记忆、遗传、社交关系、认知副本均可作为组件；对应处理逻辑由系统或插件提供。身份、事件提交、权限视图和存档重放属于引擎核心约束。

### 2.2 信息流动层

- **信息是实体**，带参数化属性；时代设定只是媒介参数的一组预设，不做"中世纪模式/赛博朋克模式"的枚举式特例。
- **事件提交事实，观察生成信息**。权威事件更新事实层；目击、报告和传播再生成各实体可获得的信息。远处势力的反应延迟来自“尚未得知”，而非事实状态尚未发生。
- **传播中带保真度衰减**：传闻每过一手可能失真，流言、误报、假情报为系统的涌现行为。
- 信息隔离问题由此被**结构性消灭**：秘密的泄漏是可模拟的事件（谁泄漏、通过什么渠道、何时到达），有完整因果链，可追查、可干预、可成为玩法。

### 2.3 模拟调度层（LOD + 热度系统）

三级精度：

| 级别 | 范围 | 模拟方式 |
|---|---|---|
| 场景内 | 玩家所在场景 | 管理者调度实体 agent；成熟规则处理稳定判定；LLM 完成扮演、叙事与语义裁定 |
| 热实体 | 场景外但保留热度 | 意图队列驱动；到期时由规则或 LLM 按事件性质裁定 |
| 宏观 | 其余世界 | 统计模型的抽象 tick（参考矮人要塞/RimWorld） |

**热度系统（已确定框架）**：

- 热度的目标：把有限的计算、事件和上下文预算投向最有助于玩家扮演体验的部分。
- 实体脱离场景后保留热度，并按冷却速度逐渐退火；系统保留热度预算与上限。
- **聚光灯效应（已确定引入）**：玩家青睐的角色更热、更难冷，在后台更多地活动。这是叙事视角的 LOD——玩家只注意聚光灯照到的地方，算力应集中在那里。
- **热度预算（当前倾向）**：系统拥有总预算和个体上限；玩家持续互动可续温。具体预算分配和冷却函数在原型阶段确定。
- **社交图传导**：社交模拟最终会产出关系网与关系圈，热度沿这张网自由传导（直接互动 > 社交邻近 > 场景共现 > 纯路人）。
- **随机升温**：保留小比例随机热度，维持世界自主性幻觉，避免玩家反推出"我一不理谁谁就变纸片人"。
- **后台事件映射（当前倾向）**：热度提高实体获得后台事件、详细裁定和重新进入玩家视野的机会；事件频率、剧烈程度与返场方式共同服务玩家扮演体验，并受角色目标、关系和世界条件约束。内部采用单一热度还是多个相关指标，属于待讨论核心。
- **调度实现（已确定方向）**：队列保存未来意图、唤醒条件及必要前提。意图到期时读取当时世界状态，再交给规则或 LLM 裁定并生成事件；实体在事件间休眠，被交互、信息到达或触发条件满足时唤醒。

### 2.4 规则层

- **成熟规则优先（已确定）**：原型建立在一套成熟桌游规则之上，直接复用其属性、检定、资源、战斗、社交和动作经济等经过验证的设计。具体规则集与授权范围待选型。
- **规则适配层（待设计）**：引擎提供世界状态、查询、行动提交和事件记录 API；规则包提供可直接使用的判定能力。目标是让玩法作者组合和配置成熟规则模块，而不是从头手写完整规则系统。
- 数值一致性由规则包与引擎共同保证（HP、物品数量、货币和所有权均有权威状态）。
- **混合判定（已确定方向）**：成熟规则处理数值与通用动作，LLM 处理说辞、欺骗、临场创造等语义条件。语义结果如何进入自动成功、自动失败、规则修正或挑战等级，仍需结合选定规则集进一步讨论。

### 2.5 LLM 接入层

- 引擎定义**"语义判定服务"抽象接口**，框架无关、接口先行。第一个实现可以是最裸的直接 API 调用；dsh 或其他框架只有在"省的轮子钱 > 适配成本"时才引入。
- **后台 agent 不一定走框架**：可以在引擎自己的程序中直接运行。
- dsh 若引入，可借用的部分：模型适配/路由、工具调用（检定做成工具）、append-only 会话日志（支撑存档/时间线分支/叙事调试）、dsh-std 兼容承诺（引擎侧只维护薄适配层）。
- **管理员 agent 与实体 agent 的权限划分（已确定）**：
  - 实体 agent 在场景内**只能获取其他实体暴露的信息**（自动披露的外貌，或交谈中引用的内容）；
  - 实体 agent **连自己的角色卡都未必全拿得到**——角色卡可有"自己不知道"的字段（隐藏诅咒、真实血统、他人评价），仅管理员可查；
  - 管理员 agent 获取实体的言行，必要时可查询一切信息；负责世界运行的规则和调度服务也拥有所需的全局查询能力；
  - 权限系统的主要目标是保持叙事一致、支持定位和纠错。跨视角查询、摘要、工具输出和 agent 交接均可记录来源，使错误发生后能够追查和修正；
  - 实体 agent 接收当前视角的投影视图；管理员和世界运行服务通过受控查询获得更完整的信息。
- **场景运行方式（已确定）**：管理者在场景内操控和调度实体 agent。引擎无需逐项模拟每个人物的全部微观行为，而是保存权威状态、提供规则能力并接收 agent 提交的行动意图。
- **场景段落是最小交互单位（已确定）**：玩家不是先选择 NPC 再发送一句话，而是用自然语言续写自己的动作、对白、内心活动和对环境的提案。玩家与 NPC 共同存在于持续运行的场景中；NPC 可以主动搭话、沉默、误解、观察或彼此交谈。
- **管理者先裁定、再按人物传递（已确定）**：玩家原文只直接进入管理者。管理者区分可观察动作、说出口的对白、玩家内心、环境提案和待裁定状态变化，随后为每个相关人物生成独立的感知包。实体 agent 不直接获得玩家整段原文，也不获得其他实体 agent 的私有调用记录。
- **管理者与实体的职责边界（已确定）**：管理者决定“该实体能感知什么、哪些事情已经成立”；实体决定“这些事情对自己意味着什么、自己准备如何回应”。管理者传递实际听见的原话、实际看到的动作、已裁定结果及必要的不确定性，不代替实体解释动机。
- **人物独立场景会话（已确定）**：每个在场人物拥有独立的 `Manager ↔ Entity` 场景会话。该人物在同一场景内历次收到的感知包、公开回应、未完成意图和轻量私有场景状态持续保留并再次注入，以维持对话连续性和利用稳定前缀缓存。
- 管理员 agent 是否拆分为“控制发生什么”与“向玩家展示”两道工序，保留为实现候选。

### 2.6 记忆系统（插件）

- **永久入库（已确定）**：人物感知并形成的记忆条目默认永久保存；人物主动选择遗忘时，条目进入遗忘状态。存储层保留必要记录以支持追踪和纠错。
- **回忆强度（当前倾向）**：记忆条目维护一个百分比或等价等级。注入 LLM 时映射为“完全记得”“记得一部分”“不太记得”；遗忘状态不进入实体 agent 的普通上下文。
- **存储与注入分离（已确定）**：降温和长期未使用主要影响检索、注入量与表述精度，不删除已保存的文本细节。
- 初版采用简易的确定性检索和分级注入。回忆强度如何变化、重复回忆如何强化、是否加入自然衰减，保留为后续记忆插件。
- 记忆作为**方法**暴露，可供各 agent 调用。

### 2.7 上下文哲学

- 每次 LLM 调用的上下文 = **为当前视角查询出来的最小充分集**，而非预堆素材。
- harness 使用目标行为、可用信息、可调用工具和输出 schema 构成正向合同。信息隔离主要由投影视图与工具权限实现。
- 人物上下文具有两个寿命层级：跨场景存在的长期人物空间，以及只在当前场景保持活跃的独立场景会话。
- 同一场景内不重复检索刚刚发生的完整对话，而是沿该人物自己的 `Manager ↔ Entity` 会话追加新消息。不同人物收到的是不同上下文，既不共享调用历史，也不共享不可见信息。
- 场景结束时关闭活跃会话，将有长期价值的内容结算为记忆、认知、关系变化、目标和后台意图。原始会话归档以供追踪，但不再普通注入；“清理”不等于删除历史。
- 特别长的场景允许在达到上下文预算后，将较早会话压成“本场景迄今摘要”，同时保留近期原文。一般场景优先保持全文连续性。
- 模型供应商的会话、KV 缓存和原始消息历史均不是角色记忆或权威状态；缓存完全失效只能影响成本和延迟，不能影响人物连续性。

### 2.8 核心对象模型（已确定最小边界）

对象模型采用“固定权威内核 + 可扩展人物工作区 + 追加事件记录”的混合结构。这里的组件化是跨引擎的纯数据合同，不要求首版引入复杂通用 ECS 框架。核心记录只使用 UUID、字符串判别字段、世界时间和可序列化数据，以便未来映射到 Web、C#、Unity、Godot 或独立服务端。

三层数据必须分开：

| 层级 | 内容 | 权威性 |
|---|---|---|
| 持久数据 | 实体、设定、状态、关系、目标、记忆、认知、意图和事件 | 权威或可追溯 |
| 调用投影 | 某人物本轮被允许看到的最小上下文 | 非权威，可重建 |
| 运行时缓存 | 拼好的提示前缀、检索索引、供应商缓存和进行中的请求 | 非权威，可全部丢弃 |

已确定的核心对象包括：

| 对象 | 职责 |
|---|---|
| 实体壳 | UUID、实体类型、名称、结构版本、记录修订号和存续状态 |
| 人物设定版本 | 人物身份、性格、价值观、背景、语言风格、能力与限制；修改时创建新版本 |
| 人物世界状态 | 地点、身体状态、物品、资源、身份和所属组织等权威状态 |
| 关系类型 / 关系实例 | 可扩展关系目录，以及人物之间实际存在的有向、多重关系 |
| 目标 | 人物当前追求、放弃、完成或被阻塞的事项 |
| 信息 | 可以被表达、传播、引用和畸变的命题，保留来源和派生链 |
| 认知 / 信念 | 某人物对一条信息相信、怀疑或拒绝的状态 |
| 记忆 | 某人物对经历或信息的长期回忆及其分级注入文本 |
| 场景 | 地点、参与者、场景时间、状态和事件序列的调度边界 |
| 人物场景会话 | 管理者与某一人物在本场景内的独立消息历史、未完成话题和私有场景状态 |
| 行动意图 | 人物、组织或系统准备尝试的动作；仍不是既成事实 |
| 裁定记录 | 保存规则或 LLM 使用的依据、输入和结果 |
| 权威事件 | 经引擎提交、能够改变事实层的事件 |
| Agent 调用记录 | 保存调用投影、模型返回、解析结果和最终提交结果，支持重试、审计和纠错 |

已确定的不变量：

- 只有人物实体可以挂载独立 `AgentMind`；地点、物品和组织可以是实体，但首版不拥有同等级独立 agent 空间。
- Agent 不是常驻模型会话，而是“持久人物资料 + 当前场景会话 + 本轮感知包”按需实例化的一次调用。
- LLM 只能提出行动意图和人物内部变更提案，不能直接改写实体或伪造权威事件。
- 任何持久状态变化必须能追溯到事件；人物认知和记忆可以错误，但不能反向覆盖世界事实。
- 场景投影和缓存没有权威性；重新生成投影不能改变游戏结果。
- 关系默认有方向，记忆遗忘默认不删除历史，重试调用不得重复提交同一结果。

观察在首版中暂不强制成为独立表；人物感知先由已提交事件、场景状态和管理者生成的感知包共同表达。只有原型显示出独立查询需求时，再提升为正式对象。

### 2.9 人物实体：固定内核与自描述工作区（已确定）

人物实体不采用一个无限膨胀的大 JSON，也不把模型聊天历史当成角色本身。人物主记录保持小而稳定，长期关系、记忆、信念和事件通过 UUID 查询。

**固定权威内核**由系统统一定义：

- UUID、实体类型、版本与修订号；
- 人物设定版本引用；
- 地点、物品、资源等世界状态；
- 关系、记忆、认知、意图和事件的基本记录合同；
- 场景会话指针、权限和 Agent 调用/回写协议。

**自描述人物工作区**允许不同人物保留适合自己的内部结构。例如酒馆老板可拥有“传闻账本”，铁匠可拥有“委托清单”，猎人可拥有“追踪线索”。每个自定义区块必须附带结构说明（Manifest），至少说明：

- 区块 ID、名称和用途；
- 内容格式；
- 可见范围；
- 何时注入；
- 谁可以提出更新。

结构说明作为该人物稳定 harness 的一部分。实体 agent 可以提出新增自定义区块；管理者或引擎检查是否重复、是否试图覆盖权威字段、说明是否足够，再生成新的 Manifest 版本。Agent 不能直接修改固定内核。

由此形成的调用层次为：

```
公共行为协议与输出合同
+ 关系类型表和必要世界规则
+ 人物工作区 Manifest
+ 人物长期设定和本轮相关工作区内容
+ 当前场景的独立 Manager ↔ Entity 会话
+ 管理者本轮感知包
```

前四部分相对稳定并适合缓存；场景会话在同一场景内追加；本轮感知包始终放在动态尾部。

### 2.10 场景感知与人物回应协议（已确定方向）

主循环为：

```
玩家自然叙述
→ 管理者拆分动作、对白、内心和世界提案
→ 引擎 / 管理者裁定已经成立的结果
→ 管理者为相关人物分别构造感知包
→ 人物 agent 返回公开行动 / 对白意图及私有状态提案
→ 管理者解决冲突并组织连续叙事
```

感知包至少需要表达：人物实际看到的动作、实际听见的原话、已经裁定的结果、不确定观察及其不确定性、与该人物直接相关的场景变化，以及本轮需要其决定的问题。人物回应至少需要区分：准备说出口的内容、准备执行的动作、尚未公开的意图，以及目标、关系、认知或自定义工作区的变更提案。

人物层第一版不要求先建立完整的事件分发系统。这里的感知包与人物回应只作为 Agent 对 Agent 的精简通信协议：管理者负责拆解玩家意图、选择应当响应的人物，并把必要信息分别发送给人物；人物只返回自己的对白、动作意图和必要的内部变化；管理者再将回应组织成玩家可见文本。

## 三、当前开发目标：人物层最小闭环

当前最重要的目标不是同时完成村庄模拟，而是先完成人物层，让玩家与角色能够在一个连续场景中自然开始对话。现有 Web Demo 只是交互外壳验证，不是目标架构：它的浏览器状态、硬编码回复和 UI 代码均可替换；真正需要沉淀的是跨引擎的数据合同、场景会话和 Manager / Entity 调用边界。

### 3.1 首个垂直切片

只实现一个地点、一个活动场景、玩家、管理者和一至两个完整人物。玩家直接续写自己的角色，不需要先选择对话对象，也不以 Galgame 式选项作为主入口。

当前冻结的最小流程：

```
玩家输入一段自然叙述
→ 管理者拆解玩家意图并选择响应实体
→ 管理者向选中的实体发起精简对话
→ 实体返回对白与动作意图
→ 管理者整理实体回应
→ 管理者向玩家输出场景文本
```

即：`玩家 → 管理者 → 实体 → 管理者 → 玩家`。

同一 Scene 内，每个人物只持续保留自己与管理者之间的精简会话。无需反复注入完整小说段落、其他人物的私有调用记录或与该人物无关的环境描写。管理者可以传递对玩家意图的理解提示，但必须将其标记为解释而非已公开事实，避免人物把管理者的推断误当成自己实际听见或看见的内容。

管理者自身维护完整的 `ManagerSceneTranscript`。它按顺序保存玩家原始角色输入、管理者感知包、实体结构化回应和管理者最终场景文本。管理者在同一 Scene 后续进行实体选择、指代消解和最终成文时持续注入这条记录，因此管理者不会因调用阶段切换而失去前文。

人物会话与管理者记录的可见性不同：某个 NPC 默认只获得自己的 `Manager ↔ NPC` 会话；管理者拥有与所有实体交谈的记录，但不必把其他 NPC 的记录直接注入当前 NPC。未来需要跨人物核对时，由管理者按实体 ID 查询对应会话，再决定可以向当前人物传递什么。

### 3.2 第一阶段必须具备的最小能力

- 一份可注入模型的人物设定；
- 一名管理者能够理解玩家输入并选择零个、一个或多个响应人物；
- 管理者能够向选中人物发送精简的语义消息；
- 人物能够返回结构化的对白和动作意图；
- 一个按人物隔离的场景会话，保留本场景 `Manager ↔ Entity` 历史；
- 管理者能够把人物回应整理成玩家可见的连续文本；
- 基本的模型输出解析、失败提示与单次重试，确保一次对话失败不会破坏当前 Scene 会话。

### 3.3 第一阶段验收标准

1. 玩家可以只写自然动作或对白，管理者能够找到应当响应的 NPC，无需玩家先点击对话对象。
2. 玩家内心活动以及其他人物的私有意图不会进入无权感知者的上下文。
3. 同一人物在同一场景后续调用中能准确接续自己与管理者先前的交流，不重复提问或忘记刚发生的内容。
4. 人物返回的对白和动作能够经过管理者整理后成为玩家可见的场景文本。
5. 最简单的单人物对话可以连续完成至少三轮而不丢失当前 Scene 中的重要信息。

### 3.5 自下而上的项目路线

项目遵循“先验证最小实体闭环，再逐层增加调度和自动生产能力”的顺序。各阶段实现必须保持纯数据合同与界面适配层分离，不能为了当前 Web Demo 把核心逻辑绑定到 React、浏览器存储或某一家模型供应商。

#### 阶段 1：单人物与物品基础层（进行中）

- 完成 `玩家 → 管理者 → 实体 → 管理者 → 玩家` 的真实 LLM 对话闭环；
- 使用灰栎村作为最小场景，世界观采用《龙与地下城》被遗忘国度的费伦大陆；
- 第一版人物提示词和管理者提示词以清晰、可验证为主，不追求复杂风格控制；
- Scene 内保存每个人物独立的 `Manager ↔ Entity` 会话；
- 建立与人物解耦的 `ItemRecord`，支持生成物品、加入人物持有物和查看完整信息；
- 对话和物品生成均通过独立服务接口调用，界面只消费稳定数据合同。

阶段验收：玩家能与至少一名角色连续交谈三轮；管理者确实完成路由与最终成文；能够生成一件符合费伦背景的物品并查看名称、类别、外观、用途、稀有度和描述。

#### 阶段 2：多人物 Scene 调度层（待开始）

- 多角色在同一 Scene 内分别获得独立上下文并作出回应；
- 响应实体激活判定；
- 人物进入、离场与 Scene 结束判定；
- 多人物响应顺序、冲突和必要的第二轮调用；
- Scene 会话的归档与最小结算。

#### 阶段 3：角色卡自动生产层（待开始）

- 从简短创作意图自动生成结构化角色卡；
- 使用 LLM 丰富人物背景、人格、关系、目标、知识边界和语言倾向；
- 自动校验、修复、版本化并产出可直接挂载 Agent 的人物实体；
- 保留人工检查与局部重生成能力。

#### 上层世界设定构建（进度待定）

人物层、Scene 调度层和角色生产管线稳定后，再制定地点、组织、事件、宏观世界状态与世界生成等上层计划。当前不提前冻结其实现顺序。

### 3.6 PC / NPC 统一人物接入（已确定）

PC 与 NPC 使用同一种人物实体、感知输入和意图输出。两者的区别只在于当前由哪一种 Controller 提供决策，不能分裂成两套人物系统。

统一调用边界：

```
ManagerPerceptionPacket
→ ActorController.requestTurn()
→ ActorTurnOutput
```

控制器至少允许以下实现：

- `HumanController`：等待真人玩家输入，并把角色内自然叙述规范化为 `ActorTurnOutput`；
- `LlmController`：根据人物设定、Scene 会话和感知包调用 LLM；
- `RuleController`：处理无需 LLM 的简单、确定性行为；
- `RemoteController`：为未来其他玩家或外部 Agent 保留接入点。

`ActorTurnOutput` 对 PC 与 NPC 保持一致，至少包含公开对白、公开动作、未公开意图和是否继续交互。管理者只依赖统一接口，不需要知道人物当前由真人、LLM、规则还是远程客户端控制。

因此同一人物可以在不同控制器间切换：PC 可临时托管给 LLM，NPC 可临时交给真人，离线角色可以参与后台仲裁，前台 Scene 与后台 Scene 也可复用同一套人物协议。

真人输入需要额外经过一层分流：角色内行动进入 `ActorTurnOutput`；玩家对故事走向、规则或创作方式的元叙事要求进入 `ManagerDirective`。二者不能混合，以免把玩家的创作要求误判为角色在世界中公开执行的动作。

现有实现中的 `EntityTurnOutput` 后续应提升为通用 `ActorTurnOutput`，现有实体专用调用器应重构为可替换的 `ActorController`。这是进入阶段 2 和后台 LLM 仲裁前的基础重构项。

### 3.7 统一术语表（已确定）

| 正式名称 | 代码建议名 | 定义 |
|---|---|---|
| 实体 | `Entity` | 世界观结构中可独立识别、保存和引用的逻辑个体，包括人物、物品、地点、组织等 |
| 人物实体 | `CharacterEntity` | 能够感知、产生意图和参与 Scene 的实体；PC 与 NPC 都属于人物实体 |
| PC | `player-controlled CharacterEntity` | 当前由真人玩家控制的人物实体；只是一种控制状态，不是独立数据类型 |
| NPC | `non-player-controlled CharacterEntity` | 当前不由真人玩家直接控制的人物实体；同样不是独立数据类型 |
| 控制器 | `ActorController` | 为人物实体提供本轮意图的可替换实现，可为真人、LLM、规则或远程客户端 |
| 管理者 | `SceneManager` | 运行时 LLM。接收玩家或实体意图，维护 Scene 上下文，选择响应实体，传递感知、协调回应并生成玩家可见场景文本 |
| 世设 GM | `WorldEditorAgent` | 独立页面中的世界设定辅助 LLM。帮助玩家查询、整理、创建和修改正典世界内容，不直接承担 Scene 内人物沟通 |
| Scene | `Scene` | 一段具有连续地点、参与实体和上下文生命周期的活动场景 |

“Agent”只用于表示具有决策能力的运行单元，不再作为所有人物或实体的泛称。PC / NPC 只描述当前控制关系；人物数据统一使用 `CharacterEntity`。界面可以显示“世设 GM”，代码与协议统一使用 `WorldEditorAgent`，避免裸 `GM` 与传统跑团中负责现场裁定的 Game Master 混淆。

职责边界：`SceneManager` 可以读取 Scene 内自身与各实体的通信记录，并在需要时查询特定实体会话；`WorldEditorAgent` 可以在管理页面查询审计记录，以帮助玩家理解、整理或修改世界设定，但任何正典修改都必须经过明确的变更操作，不能仅凭读取私有记录自动改写世界。

### 3.8 可迁移的审计数据库（已确定方向）

项目不将平台专属数据库作为核心数据模型。标准 PostgreSQL 作为持久化事实来源；Drizzle ORM 仅作为当前 TypeScript 服务端的类型安全访问层；数据库变更以普通 SQL migration 纳入源码版本控制。

部署方式：

- 本地开发与开源工程使用 Docker PostgreSQL；
- 当前无原生 TCP 连接能力的边缘部署，通过 PostgreSQL 服务商提供的 HTTP / WebSocket 驱动连接；
- 未来独立服务器可切换到标准 `pg` 连接池；
- Unity、Godot 或其他客户端不直接连接数据库，而是调用 AIRP 后端 API；
- 领域层只依赖 `NarrativeStore` / `EntityStore` 等存储接口，不依赖具体服务商 SDK。

审计数据至少拆分为：

- `scenes`：Scene 生命周期；
- `turns`：玩家每轮输入和最终场景输出；
- `transcript_entries`：管理者与实体之间可直接查询的逐条文本和结构化内容；
- `agent_calls`：模型输入、原始输出、解析输出、模型与提示词版本、耗时和 token 用量；
- `prompt_versions`：稳定提示词块与版本；
- 后续独立的角色记忆和世界事件表。

审计日志、角色记忆和世界事实必须分离：审计日志回答“模型当时看到了什么、返回了什么”；角色记忆回答“人物以后能够回忆什么”；世界事实回答“系统最终确认发生了什么”。退出 Scene 时的状态加减、记忆提炼和关系变化可以引用审计记录作为依据，但必须生成独立的结算记录，不能改写原始日志。

记录的“私有”表示叙事认知范围，而非账号授权：例如 NPC 未说出口的判断可以被 `SceneManager`、调试界面和按规则运行的离场结算读取，但不能被直接展示给普通游玩视角，也不能注入其他 NPC。`WorldEditorAgent` 是否可读取此类记录由管理页面功能明确控制。

### 3.9 当前明确不做

- 完整交易、战斗、任务和桌游规则适配；
- 自动流言传播网络；
- 热度数值与宏观世界 tick；
- 组织、国家和军队独立 agent；
- 向量数据库与复杂 RAG；
- 多玩家调度；
- 针对 Unity、Godot 或其他引擎的正式适配器；
- 权威事件日志、事件传播与可追溯事件链；
- 长期记忆检索、关系自动演化和 Scene 离场结算。

这些能力继续保留在总体架构中，但不能阻塞人物层自然对话闭环。

## 四、关键机制决策（A–F）

### A. 叙事与状态的转换层：叙事先行（已定方向）

- 目标函数是“**让玩家觉得世界在被模拟**”，不是完全的世界模拟。叙事先行指内容构思顺序；事件提交决定事实生效顺序。
- **当前倾向**：管理者先形成场景草案及候选状态操作；引擎验证并提交能够成立的变化；管理者再根据提交结果输出最终场景段落。普通对话与即时氛围描写采用轻量记录，涉及持久世界事实、承诺、泄密等后续会产生影响的内容进入事件或信息流程。
- 已知风险：漂移会累积。这是整个项目最大的技术未知数，最小闭环阶段专门试验。

### B. 玩家自由度：双对话模式（已确定）

- 角色扮演主界面采用连续场景中的自然叙述，不采用“选择 NPC → 选择台词 → NPC 回复”作为主循环。
- 玩家自然语言输入会出现规则无法映射的动作（"我把桥烧了"）。
- **双对话模式**：一类专职扮演，一类专职世界设定。
- 检测到无法映射的动作时：提醒玩家 → 生成讨论事件 → 在世界设定对话中协商解决。
- 这把"系统处理不了的输入"从失败模式变成特性（一次元协商）。语 C 圈的"控戏"禁忌在此不适用——对面是 LLM。
- 待细化：协商结论如何**正典化**。倾向"临时裁定先行、事后入库"，避免游戏节奏被配置工作打断。

### C. 持久化与事件引擎（已确定）

- **事实层唯一来源 = 引擎的确定性事件日志**；dsh 会话日志（若引入）只是可重建的派生物。
- **独立事件引擎**，API 先行：先保留数据接口，GUI/WebUI 渲染后置。

### D. 宏观粒度与实体的冷热生成（已确定）

- **角色卡惰性生成**：未与玩家交互前，宏观层可先维护人口群组或人物的最小壳状态；需要时（玩家即将遭遇 / 温度升高）再生成精英个体的完整角色卡和独立 agent 空间。
- 生成器是**带约束采样**：必须满足已有宏观统计与已对玩家叙述过的事实，不得凭空矛盾。
- **细节保存（已确定）**：已经生成并入库的文本细节继续保存。实体降温主要减少调度频率和注入 LLM 的上下文量，而非破坏性压缩原始资料。
- **可操控实体表（已确定）**：由引擎维护人物 agent 可操控的实体与动作范围（如王国 A 的统治者可控制军队 A）。归属或控制冲突发生时，由成熟规则、控制关系与必要的 LLM 社会博弈共同裁定。

### E. 多人兼容（已确定设计不变量）

- **"管理员 agent = 玩家对世界的交互页面"** 写入开发文档作为不变量。
- 一人多角色卡 = 无变化；多人同页 = 一人一张角色卡，两人输入完毕后统一运行。信息隔离架构天然支持多视角（每人只注入自己的认知视图）。

### F. 验证路径：村子原型（已确定）

长期验证范围仍是一个村子和四种设施，分别压测四条核心管线：

| 设施 | 压测内容 |
|---|---|
| 酒馆（信息集散点） | 信息流动与传播 |
| 集市 | 交易系统与规则判定 |
| 悬赏板 | 任务接口：叙事先行 + 事件回填 |
| 玩家住所 | 情感锚点：聚光灯与热度系统 |

- **当前执行顺序（已确定）**：先只完成酒馆中的人物层垂直切片，验证自然叙述、管理者感知路由、独立人物会话、人物回应和离场结算；集市、悬赏板和玩家住所暂缓。
- 人物层通过后，再依次接入信息传播、交易判定、任务事件和热度后台系统。
- 长期验收仍需定量化（如“玩家自由行动 20 轮：无状态矛盾、无越权信息、NPC 记忆一致”），符合 go/no-go 习惯。
- 引擎定型前，先用一个酒馆小场景走完整流程，暴露设计盲点。

## 五、未确定事项

按优先级排列：

1. **人物层输入 / 输出合同**
   冻结 `ManagerPerceptionPacket` 与 `EntityTurnOutput` 的 v0 字段、版本、校验范围和错误恢复方式。它们是人物自然对话实现前唯一必须先确定的数据合同。

2. **可靠调用与场景会话持久化**
   以 DeepSeek 作为首个模型实现，确定服务端调用、超时、重试、结构化解析、幂等提交、日志脱敏、场景会话追加和超长场景压缩方式。供应商细节不得进入人物权威数据。

3. **初始关系目录与扩展协议**
   确定首批态度、情感纽带和社会角色；确定新增关系类型的提案、去重、批准、版本更新和旧存档兼容方式。实体可以提出，管理者或世界规则负责正式注册。

4. **场景离场结算合同**
   明确哪些人物回应即时提交，哪些内容在离场时汇总为记忆、认知、关系、目标和后台意图；确定异常结束和重新进入场景的恢复方式。

5. **人物自描述工作区的最小 Manifest**
   确定区块说明、注入策略和更新权限的最小字段，暂不设计通用动态 schema 语言。

6. **成熟桌游规则选型与适配边界**
   需要选出原型采用的成熟规则集，并确定哪些能力直接复用、哪些由引擎 API 提供、规则包如何访问 ECS 状态，以及如何控制玩法作者的手工规则编写量。

7. **信息传播参数专题**
   已搭好讨论框架，逐项待定：
   - 媒介：速度 / 范围 / 保真度 / 可拦截性
   - 载体：人肉 / 书面 / 电磁
   - 通道拓扑：点对点 / 广播 / 沿社会网络 / 沿商路
   - 畸变模型：每手失真率
   - 信息粘性：劲爆消息传得快，平庸消息死在原地

8. **叙事→事件回填的具体实现**
   叙事先行已定，但提取器的形态、校验失败的处置（重生成？软修正？）、结构化事件 schema 均未定。是项目最大的技术未知数，村子原型阶段必须试验出答案。

9. **世界设定对话的正典化协议**
   协商结论如何写入：即时写入规则插件 vs 临时裁定事后入库（倾向前者暂缓、后者先行）。

10. **热度系统的内部模型与具体数值**
   需要决定单一热度还是多个相关指标，并确定冷却速度、预算大小、个体上限、社交传导、随机升温、后台事件频率/剧烈程度和返场机会的映射。评价标准以玩家扮演体验为中心。

11. **简易记忆系统的注入规则**
   需要确定回忆百分比的来源、分级阈值、每一级注入原文还是摘要、人物主动遗忘的触发方式，以及记忆冲突时的表现。

12. **LLM 接入层的框架选型**
   接口先行，dsh 或自研轮子的取舍延后到"裸 API 不够用"的时刻再评估。

13. **多人模式的调度实现**
   设计不变量已保留兼容，具体实现延后。

14. **内容冷启动**
   媒介参数预设、交互矩阵、角色卡模板等内容工作的规模，待村子原型后重新评估。

## 六、风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 叙事回填的状态漂移累积 | 高 | 持久事实与状态变化进入校验；村子原型专项试验 |
| 成熟规则与世界引擎适配工作量 | 高 | 先选一套规则；围绕村子垂直切片实现适配层；复用完整规则语义 |
| LLM 调用链延迟与成本 | 中 | 并行化、小模型分担叙事层、热度控制调用频率 |
| 场景内实体 agent 调度复杂度 | 中 | 管理者统一协调；引擎提供视图、规则能力和行动提交接口 |
| 管理者转述导致信息或语气损失 | 中 | 感知包保留实际听见的原话、可观察动作、来源及不确定性；管理者只过滤和裁定，不代替人物理解 |
| 人物将模型补全误当成真实记忆 | 中 | 实体在自然语言私有说明中交代欺骗、不确定性及认知依据；角色允许有意撒谎，但无依据补全不能冒充真实记忆 |
| 场景会话无限增长 | 中 | 一般场景保留全文；达到预算后压缩早期内容并保留近期原文；离场时停止注入并结算 |
| 自描述工作区发生结构漂移 | 中 | 固定权威内核；自定义区块必须带 Manifest 并经管理者或引擎批准、版本化 |
| 热实体数量膨胀 | 中 | 热度预算、个体上限与意图队列调度 |
| 玩家反推机制破坏模拟感 | 中 | 随机升温噪声、热度传导的自然梯度 |
| 耦合第三方框架的路线图 | 中 | 接口抽象，框架可替换 |
| 信息越权导致叙事错误 | 低 | 投影视图、来源记录和可追溯纠错流程 |
| 内容工作量被低估 | 低 | 先做村子，先纸面模拟 |
